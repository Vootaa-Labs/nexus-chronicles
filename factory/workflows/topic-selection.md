# Topic Selection

## Purpose / 目标

Turn a vague user direction into a writable topic that fits repository rules, persona boundaries, and target-reader value.

把用户给出的模糊方向，收敛成一个符合仓库约束、角色边界和目标读者价值的可写选题。

## Use Cases / 适用场景

当用户提供的是以下信息之一时，先走本流程，再起稿：

1. 一个宽泛方向
2. 一个零散观点
3. 一个问题
4. 一个技术点但没有明确文章角度
5. 没有给定方向，只要求从候选主题中挑选并开始

## Steps / 选题步骤

1. 识别真实意图
   用户到底是希望被解释、被说服、被提醒风险，还是被提供行业判断。

2. 判断文章任务
   这是原创、引用、回应、综述还是短评。

3. 收敛读者
   不先定义读者，就不要定题。

4. 选择角色
   角色应由任务和读者决定，而不是先入为主。

5. 形成候选题目
   至少在心里比较 2 到 3 个切口，再选一个最有信息密度的标题方向。

6. 检查证据可得性
   如果需要代码证据，先确认 `nexus-node` 或 `nexus-move` 是否能支撑这个题目。

7. 输出内部 brief
   将最终选题、目标读者、角色、文章类型、证据路线和风险点整理成一份简短 brief。

## Candidate Discovery / 自动发现候选主题

当用户不给定方向时，Agent 应优先从仓库内部发现高价值候选主题，而不是凭空起题。

优先检查以下来源：

1. `content/` 中已经存在原创，但缺少其它语言引用文章的内容缺口
2. `factory/topic-board/topic-pool.md` 中已经登记的候选主题
3. `content/indexes/topics.md`、`content/indexes/article-index.md` 与各语言索引中的主题缺口
4. `nexus-node` 与 `nexus-move` 中值得被写成专栏的代码热点
5. 尚未被整理成文章的争议点、证据点和设计边界

## No-Direction Priority / 无方向模式的决策顺序

1. 先看是否存在跨语言引用缺口
2. 再看是否存在事实源很强但文章覆盖很弱的技术主题
3. 再看是否存在适合特定角色发挥的争议或观察主题
4. 最后才从宽泛主题池中挑一个最稳的候选题

## Evaluation Standard / 选题判断标准

一个好选题至少满足三项：

1. 有明确读者价值
2. 有明确中心论点
3. 有足够证据支撑
4. 能体现角色视角差异
5. 不只是项目宣传口号

## Failure Signals / 失败信号

出现以下情况时，应重新收敛题目：

1. 标题很大，但文章只能写空话
2. 角色换谁都一样写
3. 没有明确证据路径
4. 读者定位含糊
5. 内容只是技术名词堆叠
